# Matriz de brechas frente a la plataforma de referencia

Documento de trabajo: compara la lista de capacidades que se pidió igualar con lo que el
código de este repositorio realmente hace. No es material de venta. La columna "Estado"
describe el código, no una ambición. Cada afirmación debe poder señalarse en un archivo o
en una prueba; si no, no va en esta tabla.

> **Corrección (revisión de mejora continua).** Una versión anterior de este documento
> afirmaba capacidades que el código no tiene: roles `admin/developer/viewer`, una API de Git,
> Postgres por proyecto, `docs/AGENT.md`, `runtime/backup.sh`, `SECRET_HARNESS_KEYS`,
> `resourcepolicies.harness`, registro abierto y ausencia de terminal. Se verificaron contra
> `src/server/*.ts`, `runtime/` e `infra/k8s/` y se corrigieron abajo.

## Cómo juzgar la lista

1. **¿Existe la superficie?** Si la función se puede tocar desde la API o la UI.
2. **¿Qué la respalda?** Un mecanismo real (contenedor, Kubernetes, Postgres) o una promesa.
3. **¿Qué falla primero cuando hay adversarios?** Cobrar, dejar de cobrar, un empleado
   desleal, un cliente que quiere irse.

## Plan de misión: qué significaría superar a la referencia

"Superar" no se declara, se mide. El orden prioriza lo que convierte código escrito en
capacidad demostrada; cada fase tiene un criterio de salida comprobable.

| Fase | Objetivo                                   | Criterio de salida (evidencia, no intención)                                                                                     |
| ---- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 0    | Mejora continua local                      | `npm run verify` en verde: formato, tipos, 120+ pruebas, compilación, gateway y navegador con base aislada. **Hecho.**           |
| 1    | CI activa en GitHub                        | Workflows de `infra/ci/templates/` activados por un mantenedor con permiso `workflows` y ejecuciones verdes visibles en Actions. |
| 2    | Validación en clúster real                 | Arranque, IDE, terminal, agente, publicación y parada ejecutados en Kubernetes con gVisor; checklist de `RELEASE-GATES.md`.      |
| 3    | Base de datos por proyecto                 | `DATABASE_URL` propio por proyecto, aislado por NetworkPolicy, incluido (como dump) en el bundle.                                |
| 4    | Compartir proyectos                        | Roles por proyecto con pruebas de autorización negativas (un miembro no ve lo que no le compartieron).                           |
| 5    | Despliegue independiente con rollback real | Imagen inmutable por release, despliegue que sobrevive a detener el entorno, rollback a un tag anterior probado.                 |
| 6    | Colaboración en vivo, prebuilds, billing   | Solo después de 1–5; cada una es una línea de producto.                                                                          |
